# Specs

`DESIGN.md` 讲**为什么这么设计**。这里把它拆成一件件能独立做完、独立验收的活。

按编号顺序做。每个 spec 做完都能自己验收，不需要等后面的。

| # | Spec | 做完的标志 | 依赖 |
|---|---|---|---|
| [0001](./0001-repo-skeleton.md) | 仓库骨架 | `pnpm install && pnpm verify` 通过 | — |
| [0002](./0002-first-plugin.md) | 第一个插件 + 清单校验 | 插件能构建、有单测，`pnpm verify` 能拦住写错的清单 | 0001 |
| [0003](./0003-local-install.md) | 打包自检与安装验收 | `pnpm verify:pack` 自动通过；`docs/install.md` 的手动清单你能跑通 | 0002 |
| [0004](./0004-client-preset.md) | 客户端构建 preset | jsdom 里能真正跑起来产出的 `lib/client.js` | 0001 |
| [0005](./0005-first-ui-plugin.md) | 第一个 UI 插件 | GUI 里看得见，改代码自动刷新 | 0003, 0004 |
| [0006](./0006-plugin-generator.md) | 插件生成器 | `pnpm new:plugin foo` 生成的新插件直接可用 | 0002 |

## 怎么用

每个 spec 的结构一样：

- **目标** —— 一句话
- **做完的标志** —— 能敲的命令，和期望结果
- **做什么** —— 具体步骤和文件内容
- **不做** —— 明确划出去的范围，防止越做越大

## 两个贯穿全程的约定

1. **一次只做一个 spec。** 做完、验收通过，再开下一个。
2. **验收命令必须真跑。** 没跑过的不要写"应该可以"。

## 测试分四层，每一层抓不同的错

| 层 | 在哪 | 抓什么 |
|---|---|---|
| 静态 | 0001 | 类型错误、lint、清单违规 |
| 单元 | 0002 | 插件自己的逻辑 |
| 产物契约 | 0004 | 浏览器产物能不能被加载 |
| 打包产物 | 0003 | tarball 里该有的文件在不在 |

上层过了不代表下层过。每层都要有，别互相替代。

**`dsh` 命令只有维护者能跑**（DSH checkout + nix devshell + npx）。所以"装进 profile 启动"这一环没有自动化，是 `docs/install.md` 里的手动清单。

## 已知要在实现中定论的事

只有一个：`link` 安装和 tarball 安装时，插件的依赖解析路径是否一致。0003 里用一行探针就能问清楚，**不需要提前纠结**。
